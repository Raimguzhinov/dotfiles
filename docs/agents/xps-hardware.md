# Dell XPS 13 Plus 9320 (dell-xps-13-9320)

Key quirks/helpers live in
`nixos/modules/hosts/dell-xps-13-9320/hardware.nix`.

- **Kernel**: uses `boot.kernelPackages = pkgs.linuxPackages_latest;`
  (current kernel from nixpkgs).
- **int3472 GPIO patch**: not applied (the fix is already upstream in modern
  kernels). This lowers the chance of a local kernel rebuild on
  `flake update`.

## Camera (IPU6EP)

- Uses `hardware.ipu6.enable = true` + `libcamera`.
- The default `v4l2-relayd` ipu6 instance is disabled:
  `services.v4l2-relayd.instances.ipu6.enable = lib.mkForce false`.
- Legacy applications use `v4l2loopback` and a manual `camera-bridge`.

**Important:** the claim "the camera does not recover after S4" is an
observation/hypothesis, not a 100% fact. To recheck it, a best-effort
service `xps-camera-recover` (post-resume) was added.

## Microphone (SoundWire rt714)

- `xps-mic-fix.service` applies ALSA routing at boot.
- `xps-mic-fix` has a workaround for
  `/var/lib/alsa/card0.conf.d/ctl-remap.conf`: if it turns out to be a broken symlink into
  a GC'd `/nix/store`, it is removed and an empty file is created.

## Swap and hibernation

- Swap: `/swap/swapfile` (32G) in the btrfs subvolume `swap` inside LUKS
  (`cryptroot`). `boot.resumeDevice = "/dev/mapper/cryptroot"` and
  `resume_offset` in `boot.kernelParams`.
- `resume_offset` comes from
  `btrfs inspect-internal map-swapfile -r /swap/swapfile`. When the file is
  recreated, update it, otherwise resume will not find the image.
- Do not snapshot the `swap` subvolume: btrfs refuses while the swapfile is active.
- New `resume=`/`resume_offset` values take effect only after a
  reboot. Until then logind reports `CanHibernate=na`, and
  `suspend-then-hibernate` silently becomes a plain suspend.

## Fingerprint and PAM

- The `pam_fprintd` option is spelled `max-tries=` (with a hyphen). `max_tries`
  is silently ignored. sudo: `debug max-tries=5 timeout=30`.
- The Goodix `27c6:63bc` scanner burns through attempts quickly (fprintd #217), so
  `max-tries` and `timeout` need headroom.
- ly 1.4.1 cannot log in with a fingerprint alone (codeberg ly #227), so
  `pam_fprintd` was removed from the ly stack.

## Post-resume helpers

- `xps-auth-post-resume` (restart of `fprintd` and `polkit-soteria`) was removed
  (October 2026): fingerprint failures in sudo came from the `pam_fprintd` settings, see
  "Fingerprint and PAM".
- `xps-touchpad-reset-post-resume` (unbind/bind `i2c-VEN_04F3:00`) was **removed**
  from the resume hook (October 2026): this repeated probe is exactly what hung
  the touchpad bus. The unit is kept only for manual use, and that is risky too.
- All post-resume services are started from `powerManagement.resumeCommands`
  (the `ExecStop` script of `sleep-actions.service`), not via
  `post-resume.target`: no such target exists.

## Touchpad (Elan `VEN_04F3:00 04F3:31D1`, haptic)

Chain: `i2c_designware.1` (built into the kernel, `=y`) → `i2c-VEN_04F3:00` →
`i2c_hid_acpi` → `hid-multitouch` (class `MT_CLS_WIN_8`). Nodes: `… Mouse`,
`… Touchpad`, `… UNKNOWN`. It reports no pressure; the click is generated by the firmware.

Known issues and fixes (September 2026):

| Symptom | Cause | Fix |
|---|---|---|
| After resume the cursor drifts on its own, `dmesg` floods with `i2c_designware.1: spurious STOP detected` | not reproduced since October 2026 (0 of 230 s2idle cycles). Hypothesis: touchpad emulation in the Dell EC (a second master on the bus) | used to be fixed by rebind, now rebind is forbidden (see below) |
| Touchpad dead, flood of `controller timed out` / `timeout waiting for bus ready` / `-110` | a repeated `i2c_hid` probe (unbind/bind) hangs the bus: the first read of feature report 2 after reset never completes. 4/54 rebinds after resume, 2/3 rebinds at idle, 2/6 boots where the probe ran ~60 s after the kernel (the EC held the bus until `_DSM`). SDA/SCL stay high, rebind and controller reset do not help | do not rebind; probe in initrd (`boot.initrd.kernelModules`: `pinctrl_tigerlake intel_lpss_pci idma64 i2c_hid_acpi hid_multitouch`); recovery only by hibernation via `xps-touchpad-watchdog` |
| After sleep "an extra finger is needed" (1 finger does nothing, 2 move the cursor), goes away on its own | libinput #1319: stale `is_tool_palm` on a slot after the fd is closed (lid → `tp_suspend(SUSPEND_LID)`) | libinput patch in the overlay (see below) |
| Once a day "button held down" (movement = selection/drag) | not proven; main hypothesis is a second touchpad path via PS/2 (`DLL0af3` on i8042 AUX) | `boot.blacklistedKernelModules = [ "psmouse" ]` |

- `HibernateDelaySec` and `HibernateMode=shutdown` are set in
  `systemd.sleep.settings.Sleep`, not in logind: logind ignores this
  key. Until October 2026, because of this, `suspend-then-hibernate` never
  hibernated, and the laptop with the lid closed slept in s2idle until the battery
  drained ("limbo"). `shutdown` bypasses the Dell firmware S4 path.
- `services.upower.criticalPowerAction = "Hibernate"`: the default
  `HybridSleep` at 2% left the machine in s2idle on an empty battery
  (one of the touchpad failure triggers, plus hybrid-sleep 25.09 lost the session).
- **Do not use** `modprobe -r i2c_designware_*` (the nixos-hardware script
  `sleep-resume/i2c-designware`): the module is built in, `modprobe -r` is a
  no-op for it, and nothing loads `i2c_hid_acpi` afterwards, so the touchpad is dead until
  reboot. This is exactly what "broke the touchpad" in the old attempt.
- `tap = false`, `dwt = false` in niri: tap-and-drag/drag-lock have nothing to do
  with the stuck button.
- `xps-touchpad-watchdog`: on the line `i2c-VEN_04F3:00: failed to` in the
  kernel journal it runs an active check (`HIDIOCGFEATURE` report 2 via
  `hidraw`) and, only if the touchpad does not respond, runs `systemctl hibernate`
  (at most once per 10 minutes). Errors logged while entering hibernation
  arrive in the journal after resume with fresh timestamps. So relying on the journal
  alone is wrong: it causes a double hibernation.
- Tested and **does not work**: a pause after HID RESET in `i2c-hid`
  (out-of-tree patch, 300 ms), I2C1 controller reset, 9 SCL clocks
  (the lines are not held low). In ACPI the touchpad has neither a power nor a reset pin.
- Stress test rig: `.claude/skills/xps-touchpad-debug/stress/`
  (`run.sh OUT [default|t2a|ec]`). It never hibernates; on a
  hang it stops with exit code 3.

Diagnostics at the moment of failure: the skill `.claude/skills/xps-touchpad-debug`
(local, `.claude` is in gitignore). Key point: compare the kernel state
(`EVIOCGMTSLOTS`/`EVIOCGKEY` on `/dev/input/eventN`) with a fresh
`libinput debug-events` and with niri's behavior; this immediately splits the bug into
firmware/kernel/compositor libinput.

## Temporary upstream patches (remove once they land in nixpkgs)

- **libinput `d0e6d43a` ("touchpad: sync the slot's tool type when syncing
  touch state", issue #1319, MR !1505)**: in `nixos/modules/overlays.nix`
  it is mixed only into `niri-unstable` (the only niri in the system,
  no mass rebuild). The fix is in libinput ≥ 1.31.901 / 1.32.0.
  On `nixos-rebuild` the overlay itself prints `warning: overlays.nix: libinput …
  already contains d0e6d43a` as soon as nixpkgs has libinput ≥ 1.31.901.
  Manual check:
  `nix eval --raw ~/dotfiles/nixos#nixosConfigurations.raimguzhinov.pkgs.libinput.version`.
  Saw the warning: remove `let libinput = …` and the `niri-unstable` override
  from the overlay (keep only `doCheck = false` on `niri`).
  If `fetchpatch` stops applying (the patch is already included), that is the same
  signal.
- niri: the only package is `niri-unstable`, set in NixOS
  `programs.niri.package` (`configuration.nix`). The niri-flake NixOS module
  forces its own package into HM via `mkForce`, so do not set `package` in HM
  (`niri.nix`): it is ignored. The module default is `niri-stable`;
  without an explicit `programs.niri.package` it will silently fall back to it.
